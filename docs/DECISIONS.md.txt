## Decision Log

### 2026-06-09

Decision:
The project will focus on reducing cognitive load rather than maximizing automation.

Reason:
The primary problem is information overload and remembering responsibilities, not lack of automation.

### 2026-06-09

Decision:
The system will be designed as an external brain rather than a collection of agents.

Reason:
The long-term goal is decision support and memory augmentation rather than isolated task automation.

---

### 2026-06-09

Decision:
V1 will prioritize capture and organization.

Reason:
Reliable capture is required before recommendations or automation can be trusted.

---

### 2026-06-09

Decision:
Recommendations will be prioritized before autonomous actions.

Reason:
Trust must be established before automation becomes valuable.

---

### 2026-06-09

Decision:
Architecture decisions will be driven by problems rather than technology trends.

Reason:
The project should remain useful even if underlying technologies change.

### 2026-06-09

Decision:
Use Telegram as the initial mobile capture interface.

Reason:
This provides the simplest always-on capture system while keeping costs low and avoiding the need for my laptop to remain online.

Consequences:
This makes Telegram a temporary V1 ingestion channel rather than a permanent architectural dependency. The data model should remain source-agnostic so future interfaces and integrations can use the same underlying system.

Follow-Up Required:
Define capture message formats and authentication for bot-based ingestion.

### 2026-06-09

Decision:
Use a Cloudflare Worker as the public webhook endpoint.

Reason:
A Cloudflare Worker provides a simple always-on public entry point without requiring dedicated infrastructure or a local machine to remain online.

Consequences:
The app can accept incoming Telegram webhooks reliably while keeping the infrastructure footprint low.

Follow-Up Required:
Configure the worker to validate Telegram requests and forward payloads into the processing pipeline.

---

### 2026-06-09

Decision:
Use Cloudflare D1 as the primary structured data store.

Reason:
D1 provides a lightweight SQL-compatible managed database that fits the low-cost, simple-stack V1 requirement.

Consequences:
Structured captures and review items can be stored centrally, enabling remote access and future interface expansion.

Follow-Up Required:
Design the D1 schema to support tasks, decisions, waiting-on items, references, and metadata.

### 2026-06-09

Decision:
The External Brain should eventually have one primary user-facing interface for direct interaction and review.

Reason:
The purpose of the project is to reduce cognitive load. Requiring me to communicate with the system through multiple apps or check multiple dashboards would recreate the fragmentation the system is meant to solve.

Consequences:
Telegram should be treated as a replaceable ingestion channel rather than a permanent architectural dependency. The data model should remain source-agnostic so future interfaces and integrations can use the same underlying system.

Follow-Up Required:
Define the future primary interface and plan how Telegram and other inputs feed into it.

### 2026-07-25

Decision:
Serve a temporary responsive review dashboard as static assets from the existing Cloudflare Worker, keep its API and Telegram webhook in the same Worker project, and use D1 as their shared source of truth. Protect the dashboard assets and API with HTTP Basic authentication backed by Worker secrets.

Reason:
Requiring Cloudflare console access and manual SQL queries recreates the cognitive burden the project exists to remove. Reusing the deployed Worker and D1 database provides an always-on phone and desktop interface without adding another service or requiring a local computer.

Consequences:
The Worker is responsible for Telegram ingestion, authenticated dashboard API routes, and protected static assets. Telegram captures can be reviewed and categorized from an Inbox, and structured items can be completed or reopened remotely. HTTP Basic authentication is accepted as a deliberately small single-user V1 control and should not be treated as the final identity architecture. The dashboard remains replaceable as the future primary interface becomes clearer.

Follow-Up Required:
Validate the dashboard and authentication on phone and desktop during the one-week field test. Reassess authentication before adding users, sensitive integrations, or broader access.

### 2026-07-25

Decision:
Adopt the V1.1 item model with one primary work category separated from optional domain, requester, project, flags, and due date/time metadata. Use the statuses Inbox, Open, Waiting, Done, and Archived. New Telegram and dashboard captures create an uncategorized Inbox item immediately, and categorization remains manual.

Primary categories:
Procurement; Admin & Finance; Communication & Follow-Up; Scheduling & Coordination; Project Work; Problems to Solve; Research / Figure Out; General Task.

Reason:
The original type list mixed work classification with state and did not support useful cross-cutting views such as open items requested by Dan. Separating these dimensions keeps capture fast while enabling later filtering without adding automated classification or forcing premature decisions.

Consequences:
Every saved capture has an item record and can be reviewed immediately. Inbox items may temporarily lack a primary category so classification never blocks capture; categorized active items require one primary category. Domain, requester, project, flags, due time, and status can change without altering the preserved raw capture. The dashboard supports Done/Reopen, Waiting, Archive, and explicitly confirmed permanent deletion. Telegram category commands from the prototype are no longer interpreted automatically.

Follow-Up Required:
Evaluate category clarity, metadata usefulness, Inbox accumulation, and deletion behavior during the field test. Add saved filtered views such as a Dan Queue only after real usage demonstrates their value.

### 2026-07-26

Decision:
Health Connect data will be read through a small read-only Android companion app and synchronized into shared External Brain health infrastructure. The Cloudflare Worker and Sunday Review Agent will not attempt to access the device-local Health Connect store directly. The initial integration will cover steps, sleep, exercise sessions, food and nutrition (including available micronutrients), hydration, weight, and resting heart rate when reliably supplied by connected sources. Medical records, exercise routes/GPS, and other data without a clear planning purpose are excluded initially.

Health data will use tiered retention and deterministic compaction:

- retain individual food, water, sleep, and other useful event-level detail for 90 days;
- retain daily summaries for approximately two years;
- retain weekly summaries for approximately five years;
- retain compact monthly summaries indefinitely;
- retain low-volume measurements such as one daily weight value longer when storage cost is negligible;
- preserve counts, coverage, missing days, sums, averages, ranges, and variability so summaries can be merged and updated without keeping every source record;
- compact or delete detailed records only after the replacement summary is successfully written and verified.

Micronutrients will be stored sparsely in daily summaries: only nutrients actually supplied by Health Connect are recorded, and missing values remain missing rather than becoming zero. Individual food descriptions do not need indefinite retention.

Only current nutrition and hydration targets will be stored. Targets are edited in place; historical target versions and historical target-attainment claims will not be maintained. Historical observations may be compared with the current target only when the output explicitly labels that comparison as using the current target.

Reason:
Health Connect is device-local and permission-controlled, so an Android client is required. Weekly planning benefits from recent detail and long-term trends, but retaining years of high-frequency raw records would add privacy, storage, and maintenance cost without proportional value. Tiered summaries preserve useful trends and data-quality context while minimizing retained sensitive data.

Consequences:
Shared health data belongs to the External Brain rather than to the Sunday Review Agent. The Android app must request granular read permissions, historical-read permission for the one-time backfill, and optional background-read permission for incremental synchronization. Historical backfill must be resumable and chunked. Incremental sync must handle updates and deletions idempotently. Sunday Review may consume a dated health summary and ask for subjective energy, stress, pain, illness, recovery, and capacity that Health Connect cannot establish.

Follow-Up Required:
Build an Android proof of concept that reads a selected seven-day range locally before introducing cloud ingestion. Confirm which micronutrients the phone's current source applications actually populate. Define shared health tables, phone pairing and revocation, sync authentication, correction windows, compaction scheduling, and deletion/rebuild behavior before production health data is uploaded.

### 2026-07-26 — Initial Health Sync Contract

Decision:
The first durable Health Connect sync stores one canonical summary per device, local calendar date, and timezone in shared D1 infrastructure. Uploads use idempotent replacement so a repeated backfill corrects the same day instead of duplicating it. Missing measurements remain null, micronutrients remain sparse, exercise types are stored under friendly canonical names, and source-package coverage is retained.

The Android companion authenticates with a dedicated revocable bearer token stored as a Worker secret and embedded only in a locally built APK. It does not reuse dashboard or Telegram credentials. Rotating or removing the Worker secret revokes the device. The initial manual backfill covers the 30-day window Health Connect makes available on the current phone and uploads only when explicitly requested.

Reason:
A daily contract is the smallest useful durable input for Sunday Review and establishes correction, provenance, and missing-data behavior before background sync or destructive compaction exists.

Consequences:
Daily summaries can be safely re-read and replaced as source applications correct recent records. This first table is not the event-detail tier and does not yet implement scheduled incremental sync, 90-day event deletion, weekly/monthly rollups, current targets, or Sunday Review packet consumption. Production device access is single-token initially; a multi-device pairing registry is deferred until a second device or self-service revocation requires it.

Follow-Up Required:
Validate the first 30-day backfill and source coverage, then add read-only weekly summary consumption for Sunday Review. Add scheduled incremental synchronization and deterministic weekly/monthly compaction before claiming the full retention design is operational.
